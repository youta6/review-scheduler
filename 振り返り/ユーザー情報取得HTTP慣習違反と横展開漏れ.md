# ユーザー情報取得 — HTTP慣習違反・設計漏れ・テストケース漏れ・実装漏れ

作成日：2026/6/22

参照指摘表：
- `レビュー指摘表/結合テスト工程/テスト実施中/ユーザー操作/ユーザー情報取得_v0.1_レビュー指摘表.md`（No.1〜No.4）

---

## 考慮漏れ（1）：GET のリクエストボディでユーザー情報を絞り込んでいた

### 発生した問題

`GET /users/{user_id}` のエンドポイントが、取得対象の識別子として `UserGetRequest`（リクエストボディ）の `user_name` を使用していた。HTTP の慣習（RFC 9110）では GET にリクエストボディを持たせることは推奨されておらず、OpenAPI Specification 3.x では GET の `requestBody` を明示的に禁止している。また URL に `{user_id}` が既に存在するにも関わらず、それを無視してボディで識別子を受け取る設計は REST 原則にも反していた。

### 本来どの工程で発見すべきだったか

**設計工程**で発見すべきだった。

REST 原則では「リソースは URL で識別する」とされており、`{user_id}` が URL に含まれる時点でリクエストボディの `user_name` は冗長かつ不適切だった。設計書を作成する際に、HTTP メソッドとリクエスト形式の適合性を確認する手順が必要だった。

### 見落とした理由

リクエストボディを使えば Pydantic によるバリデーションが自動化でき、実装が簡単に見えた。URL パスパラメータで受け取ることで同様のバリデーションが可能であるという認識が不足していた。

### 教訓

- GET・DELETE の識別子は URL パスパラメータで受け取る（リクエストボディは不要）
- URL に `{user_id}` 等のパスパラメータが存在する場合、その値をエンドポイント内で使う
- 参考: ユーザー情報削除でも同様の指摘（No.1）があり、横展開で本件を発見した

## 考慮漏れ（2）：設計書にバリデーションエラー表が未記載

### 発生した問題

`user_id` をパスパラメータ（int型）に変更したにも関わらず、設計書の引数定義にバリデーションエラー表（user_id が整数以外の場合 → HTTP 422）を追加しなかった。ユーザー作成設計書には同様のバリデーションエラー表が存在しており、記載の統一が必要だった。

### 本来どの工程で発見すべきだったか

**設計書更新時**に発見すべきだった。

ユーザー作成設計書を参照すれば、引数定義の下にバリデーションエラー表を記載するパターンが確認できた。設計変更後に他のエンドポイントの設計書と照合する手順が抜けていた。

### 見落とした理由

旧実装では `UserGetRequest`（Pydantic BaseModel）がバリデーションを暗黙的に担っており、設計書上に明示的なバリデーションエラー表が不要だった。パスパラメータに変更することで FastAPI が型チェックを自動送出するようになったが、その変化に伴う設計書の追記を意識できていなかった。

### 教訓

引数の受け取り方（リクエストボディ → パスパラメータ）を変更した場合、バリデーションエラーの発生条件・発生源が変わる。設計書を更新する際は、同種のエンドポイント（ユーザー作成など）の設計書を参照し、記載パターンが統一されているか確認する。

## 考慮漏れ（3）：結合テスト仕様書にバリデーションエラーのテストケースが未記載

### 発生した問題

`user_id` をパスパラメータ（int型）に変更したにも関わらず、結合テスト仕様書にバリデーションエラー（`GET /users/abc` など整数以外の値 → HTTP 422）のテストケースを追加しなかった。ユーザー作成結合テスト仕様書には同様の 422 テストケースが含まれており、テストケース設計の統一が必要だった。

### 本来どの工程で発見すべきだったか

**テスト仕様書更新時**に発見すべきだった。

設計書更新の際にバリデーションエラー表を追加していれば、その時点でテスト仕様書への 422 テストケース追加も連動して気づけた。また、他の結合テスト仕様書との比較確認でも発見できた。

### 見落とした理由

パスパラメータに変更したことで 422 が発生するケースができたが、テストケースへの反映を失念した。ユーザー情報削除でも同じ漏れが発生しており、横展開時に繰り返されたミスとなった。

### 教訓

引数の型を持つパスパラメータを追加・変更した場合、型不一致のテストケースを結合テスト仕様書に追加する。既存テスト仕様書（ユーザー作成など）の 422 テストケースの記載パターンを踏襲する。

## 考慮漏れ（4）：使用しなくなった UserGetRequest が schemas.py に残存

### 発生した問題

エンドポイントを `UserGetRequest`（リクエストボディ）からパスパラメータ `user_id: int` に変更したにも関わらず、`schemas.py` に `UserGetRequest` クラスの定義が残存しており、デッドコードになっていた。

### 本来どの工程で発見すべきだったか

**実装修正時**に発見すべきだった。

エンドポイント実装を修正する際に、対応して不要になったスキーマを削除する手順が漏れていた。ユーザー情報削除でも同じ漏れ（`UserDeleteRequest` の残存）が発生しており、横展開時に繰り返されたミスとなった。

### 見落とした理由

エンドポイントの修正に注力してしまい、使用されなくなったスキーマの削除が抜け落ちた。スキーマが残っていてもエラーにならないため、単純なデッドコードとして見落としやすかった。

### 教訓

エンドポイントの引数形式を変更した際は、変更前に使用していたスキーマが他の場所でも使用されていないかを確認し、デッドコードになっているものは削除する。
