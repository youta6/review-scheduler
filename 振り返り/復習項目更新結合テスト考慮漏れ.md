## 考慮漏れ：必須パラメータ欠落（review_id なし）のテストケースが未作成

### 発生した問題

リクエストボディが空（`{}`）で必須パラメータ `review_id` 自体が存在しない場合の HTTP 422 テストケースが未作成だった。

既存の No.4「全更新項目未入力」は `{"review_id": 1}` を含むケース（任意フィールドがすべて未指定）であり、`review_id` 自体の欠落ケースとは別の分岐。

### 本来どの工程で発見すべきだったか

**テスト仕様書作成時**に発見すべきだった。

引数定義で `review_id` が必須（`ge=1, le=99`）と明記されており、確認していれば作成時点で網羅できた。

### 見落とした理由

「入力未設定」を No.4（任意フィールドの未指定）で代表させており、それとは独立した「必須パラメータ自体の欠落」というケースを別途テストする必要があることを見落とした。

### 教訓

バリデーション異常系は以下を区別して設計する。
- **必須パラメータの欠落**：パラメータ自体が存在しない → HTTP 422
- **任意パラメータの未指定**：必須パラメータは存在するが任意フィールドがすべて空 → ビジネスロジックの HTTP 422

両者は通過するバリデーション層が異なるため、それぞれ独立したテストケースが必要。

## 考慮漏れ（2）：削除済みユーザーによるアクセスのテストケースが未作成

### 発生した問題

参照指摘表：`レビュー指摘表/結合テスト工程/テスト仕様書レビュー/復習項目操作/復習項目更新_v0.1_レビュー指摘表.md`（No.3）

JWT トークン取得後にユーザーが削除された場合（delete_flag=true）に HTTP 403 が返ることを確認するテストケース（No.8）が未作成だった。

### 本来どの工程で発見すべきだったか

**テスト仕様書作成時**に発見すべきだった。

認証・認可が必要なエンドポイントでは、ユーザー存在チェック（有効ユーザー検証）が認証処理に含まれており、この観点を確認していれば作成時点で網羅できた。

### 見落とした理由

認証異常系として「未認証（トークンなし）」は意識できているが、「認証済みだが削除済みユーザー」というケースが別の異常系として存在することを見落とした。JWT トークンは発行後も有効期限内は使用できるため、ユーザー削除とトークン有効性を切り離して考える観点が不足していた。

### 教訓

認証・認可が必要なエンドポイントのテストケースには、以下を独立した異常系として含める。
- トークンなし → HTTP 401
- 削除済みユーザーのトークン → HTTP 403（ユーザー存在チェック失敗）

## 考慮漏れ（3）：存在しない review_id を指定した場合のテストケースが未作成

### 発生した問題

参照指摘表：`レビュー指摘表/結合テスト工程/テスト仕様書レビュー/復習項目操作/復習項目更新_v0.1_レビュー指摘表.md`（No.1）

値は範囲内（1〜99）だがDBに未登録の `review_id` を指定した場合に HTTP 404 が返ることを確認するテストケース（No.9）が未作成だった。

### 本来どの工程で発見すべきだったか

**テスト仕様書作成時**に発見すべきだった。

設計書の処理概要に `review_id` のDB存在確認と HTTP 404 のレスポンスが明記されており、確認していれば作成時点で網羅できた。

### 見落とした理由

`review_id` の異常系として「値が範囲外（> 99）→ HTTP 422」は意識できていたが、「値は範囲内だがDBに未登録」というケースが別の分岐（バリデーション層でなくDB照合層）で処理されることを見落とした。

### 教訓

数値パラメータの異常系は以下を区別して設計する。
- **値の範囲外**：Pydantic バリデーション → HTTP 422
- **値は範囲内だがDBに未存在**：DB照合エラー → HTTP 404

両者は別のバリデーション層で処理されるため、それぞれ独立したテストケースが必要。

## 考慮漏れ（4）：URLパスのパラメータが無視される実装挙動の確認テストが未作成

### 発生した問題

参照指摘表：`レビュー指摘表/結合テスト工程/テスト仕様書レビュー/復習項目操作/復習項目更新_v0.1_レビュー指摘表.md`（No.4）

エンドポイント関数の引数に `{user_id}` と `{review_id}` が宣言されておらず、URLパスのパラメータは実装上無視される。URLの `review_id` とボディの `review_id` が異なる場合にボディの値が優先されることを確認するテストケース（No.10）が未作成だった。

### 本来どの工程で発見すべきだったか

**テスト仕様書作成時**に発見すべきだった。

実装コードを確認すればエンドポイント関数の引数定義でURLパスのパラメータが宣言されていないことが分かり、この挙動を確認するテストケースを作成できた。

### 見落とした理由

テスト仕様書を設計書のエンドポイント仕様のみを参照して作成しており、実装コードの引数定義まで確認できていなかった。URLパスのパラメータが実際に使われているかどうかを検証する観点が欠けていた。

### 教訓

URLパスにパラメータを持つエンドポイントでは、実装コードの引数定義を確認し、パスパラメータが実際に使用されているかを検証するテストケースを含める。パスパラメータとボディパラメータが同名の場合は特に、どちらが優先されるかを明示的に確認する。

## 考慮漏れ（5）：削除済みユーザーアクセス時のエラーメッセージを誤認識

### 発生した問題

参照指摘表：`レビュー指摘表/結合テスト工程/テスト仕様書レビュー/復習項目操作/復習項目更新_v0.1_レビュー指摘表.md`（No.5）

テスト仕様書 No.8（削除済みユーザーによるアクセス）の想定結果に `{"detail": "権限がありません"}` と記載したが、正しくは `{"detail": "削除済みユーザーのため更新できません"}` だった。

### 本来どの工程で発見すべきだったか

**テスト仕様書作成時**に発見すべきだった。

実装コードの HTTP 403 レスポンス定義を参照すれば正しいメッセージを確認できた。

### 見落とした理由

エラーメッセージを設計書や実装コードで確認せず、類似のメッセージ（`"権限がありません"`）を推測で記載してしまった。

### 教訓

異常系テストケースの想定結果に含まれるエラーメッセージは、必ず実装コードの `raise HTTPException(...)` や `detail=` 引数を確認して転記する。推測で記載しない。
