# テスト仕様書とテストコードの乖離

作成日：2026/6/22

参照テスト仕様書：
- `test_specification/integration_test_specification/ユーザー操作/ユーザー情報取得_結合テスト仕様書.md`（No.1）

---

## 発生した問題

結合テスト仕様書 No.1 の想定結果に `{"user_id": 1, "user_name": "testuser", "delete_flag": false, "user_kind": "一般", ...}` と記載されていた。しかし実装したテストコードでは以下の乖離があった。

| 仕様書の想定結果 | 実装したアサーション |
|---|---|
| `"user_id": 1` | `assert "user_id" in body`（値を確認せず存在チェックのみ） |
| `"created_at": ...` | `assert "created_at" in body`（値を確認せず存在チェックのみ） |
| `"updated_at": ...` | `assert "updated_at" in body`（値を確認せず存在チェックのみ） |

再鑑者（youta6）の確認で発見し、以下に修正した。

```python
assert body["user_id"] == 1          # 値まで確認
assert body["created_at"] is not None # Noneでないことを確認
assert body["updated_at"] is not None # Noneでないことを確認
```

---

## 本来どの工程で発見すべきだったか

**テストコード実装時**に発見すべきだった。

テストコードを書く際に、テスト仕様書の想定結果と1項目ずつ照合する手順が必要だった。仕様書を参照しながらコードを書いていれば、`"user_id": 1` と明記されているのに値チェックを省いていることに気づけた。

---

## 見落とした理由

`"created_at"` や `"updated_at"` のような予測できないタイムスタンプのフィールドは「存在チェックで十分」という判断が先行し、それと同じパターンで `"user_id"` も `assert "user_id" in body` と書いてしまった。`user_id` は値が確定している（`=1`）にもかかわらず、タイムスタンプと同列に扱ってしまった。

---

## 教訓

テストコードを実装する際は、テスト仕様書の想定結果を1フィールドずつ見ながらアサーションを書く。

- 値が確定しているフィールド（`user_id`, `user_name`, `delete_flag`, `user_kind` など）は **値まで確認する**（`assert body["user_id"] == 1`）
- 値が予測できないフィールド（`created_at`, `updated_at` など）は **None でないことを確認する**（`assert body["created_at"] is not None`）
- 「存在チェックで十分」という判断は、仕様書に値が明記されていないフィールドにのみ適用する

仕様書に `"user_id": 1` と書いてあれば、コードでも `== 1` で検証する。仕様書とコードは1対1で対応させる。
