# レスポンスのフィールド内容確認漏れ

作成日：2026/6/23

参照テスト仕様書：
- `test_specification/integration_test_specification/ユーザー操作/全ユーザー情報取得_結合テスト仕様書.md`（No.1・No.2）

---

## 発生した問題

結合テスト仕様書 No.1・No.2 の想定結果が以下の内容に留まっており、UserGetResponse の各フィールドが正しく返却されることを確認していなかった。

| 項番 | 修正前の想定結果 |
|---|---|
| No.1 | HTTP 200、全登録ユーザーを含む UserGetResponse のリスト |
| No.2 | HTTP 200、testuser のみを含む1件のリスト |

テストコードも同様に、件数・user_name・user_kind のみをアサーションしており、`user_id`・`delete_flag`・`created_at`・`updated_at` の確認が抜けていた。

再鑑者（youta6）の指摘により、仕様書の想定結果とテストコードに全フィールドの確認を追加した。

---

## 本来どの工程で発見すべきだったか

**テスト仕様書作成時**に発見すべきだった。

想定結果を書く際に「HTTP 200 が返ること」と「件数が正しいこと」だけを意識し、レスポンスボディの各フィールドが仕様通りであることの確認を失念した。

---

## 原因

「管理者は全件返却、一般ユーザーは自分のみ返却」というフィルタリング動作の確認に観点が集中し、UserGetResponse の中身（各フィールドの値）が正しく返されているかという観点を見落とした。

---

## 教訓

レスポンスを返すエンドポイントのテストでは、以下の3つを必ず確認する。

1. **ステータスコード**：期待する HTTP ステータスが返ること
2. **件数・構造**：リストの件数、オブジェクトの存在など
3. **フィールドの値**：レスポンスの各フィールドが仕様通りの値であること
   - 値が確定しているフィールド（user_id, user_name, delete_flag, user_kind）→ 値まで確認
   - 値が予測できないフィールド（created_at, updated_at）→ null でないことを確認

3 を省くと「レスポンスが返ってきた」ことは確認できても「正しいレスポンスが返ってきた」ことを保証できない。
