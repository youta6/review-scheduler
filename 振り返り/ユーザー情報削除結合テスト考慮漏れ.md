作成日：2026/6/20

対象テスト仕様書：`テスト仕様書/結合テスト仕様書/ユーザー操作/ユーザー情報削除_結合テスト仕様書.md`

## 考慮漏れ：URLパスの user_id が無視される実装挙動の確認テストが未作成

### 発生した問題

エンドポイント関数の引数に `{user_id}` が宣言されておらず、URLパスのパラメータは実装上無視される。異なる `user_id` を URL に指定しても常に認証ユーザー（JWT）自身が削除対象となることを確認するテストケース（No.6）が未作成だった。

### 本来どの工程で発見すべきだったか

**テスト仕様書作成時**に発見すべきだった。

実装コードを確認すればエンドポイント関数の引数定義に `user_id` が含まれていないことが分かり、URLパスのパラメータが実際に使用されているかを検証するテストケースを作成できた。

### 見落とした理由

テスト仕様書を設計書のエンドポイント仕様のみを参照して作成しており、実装コードの引数定義まで確認できていなかった。URL に `{user_id}` が含まれていれば当然削除対象の特定に使用されると思い込んでいた。

### 教訓

URLパスにパラメータを持つエンドポイントでは、実装コードの引数定義を確認し、パスパラメータが実際に処理で使用されているかを検証するテストケースを含める。特に認証情報（JWT）とURLパスパラメータの両方でユーザーを特定できる場合、どちらが優先されるかを明示的に確認する。

## 考慮漏れ（2）：リクエストスキーマのパラメータ必須/任意の確認漏れ

### 発生した問題

参照指摘表：`レビュー指摘表/結合テスト工程/テスト仕様書レビュー/ユーザー操作/ユーザー情報削除_v0.1_レビュー指摘表.md`（No.4）

`UserDeleteRequest` の `user_name` が `UserBase` の継承により必須フィールドになっていたが、設計書では任意項目（必須 = `-`）と定義されている。その結果、`user_name` 未指定時の想定結果をスキーマバリデーションエラー（HTTP 422）と誤って認識し、テスト仕様書 No.5 を異常系として作成してしまった。正しくは JWT ユーザー自身が削除される正常系（HTTP 200）である。

対応として以下を修正した：
- `app/schemas.py`：`UserDeleteRequest` を `BaseModel` 直接継承に変更し、`user_name` を `str | None = Field(default=None, ...)` に修正
- テスト仕様書 No.5：テスト項目を「正常系 - user_name 未指定で認証ユーザー（JWT）を削除」、想定結果を HTTP 200 に修正

### 本来どの工程で発見すべきだったか

**テスト仕様書作成時・スキーマ実装時**に発見すべきだった。

設計書の引数定義で `user_name` の必須欄を確認していれば、スキーマを正しく Optional に実装し、テストケースも正常系として作成できた。

### 見落とした理由

`UserDeleteRequest` を `UserBase`（`user_name` 必須）の継承で実装しており、設計書の必須/任意の定義を照合せずにテスト仕様書を作成した。既存の親クラスを継承する際に、フィールドの必須/任意が変わる場合があることを意識できていなかった。

### 教訓

スキーマの親クラス継承時は、設計書の引数定義（必須 = ○/- ）と継承後のフィールド定義が一致しているか確認する。テスト仕様書作成時も、各パラメータの必須/任意をスキーマ実装と設計書の両方で確認してからテストケースを設計する。
