## 考慮漏れ（1）：メソッド名が設計書と不一致

### 発生した問題

設計書では `get_user_endpoint` と定義されているが、実装では `read_user_endpoint` となっていた（`main.py:260`）。

```python
# main.py:260（単体テスト時点）
@router.get("/user")
async def read_user_endpoint(  # ← 設計書は get_user_endpoint
    ...
```

### 本来どの工程で発見すべきだったか

**実装工程のコードレビュー**で発見すべきだった。

設計書のメソッド名と実装コードのメソッド名を照合するレビューで発見できる性質の問題。実装工程レビュー・再鑑のいずれでも見落とされ、単体テストのテストコード記述時に設計書と実装を突き合わせて初めて判明した。

### 見落とした理由

実装工程レビューで、設計書に記載されたメソッド名と実装コードのメソッド名を 1 対 1 で照合する確認が行われなかった。メソッドの動作内容には問題がなかったため、名前の不一致に気づきにくかった。

## 考慮漏れ（2）：`UserGetRequest.user_name` が任意項目なのに必須扱い

### 発生した問題

`UserGetRequest.user_name` は検索条件として任意（指定なしで全件取得の変形）であるが、`UserBase` を継承しているため `user_name` が必須フィールドとして扱われていた（`schemas.py:77`）。

```python
# schemas.py:77（単体テスト時点）
class UserGetRequest(UserBase):  # UserBase は user_name が必須
    pass
```

`UserGetRequest` は `UserBase` を継承せず、`user_name: str | None = None` のように独立して定義するか、`UserBase` 側で `user_name` をオプションにする設計変更が必要。

### 本来どの工程で発見すべきだったか

**実装工程のコードレビュー**で発見すべきだった。

設計書で `user_name` が任意項目と明記されている場合、継承元クラスの影響でフィールドが必須扱いになっていないかをレビューで確認すべきだった。単体テストでリクエストを組み立てる際に、`user_name` を省略するとエラーになることで発覚した。

### 見落とした理由

`UserBase` を継承するクラスを追加した際、継承元の必須フィールドが継承先でも必須になるという Python/Pydantic の挙動を考慮したレビューが行われなかった。設計書の「任意」という記載と実装が乖離していないかの確認が不足していた。

### 教訓

Pydantic モデルで継承を使う場合、継承元の必須フィールドが継承先の仕様（任意・必須）と一致しているかを設計書と照らし合わせて確認する。任意項目を持つクラスが必須フィールドを持つクラスを継承する場合は、`Optional` への変更またはオーバーライドが必要になる。
