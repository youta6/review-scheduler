# 復習項目削除 — HTTP慣習違反・設計漏れ・テストケース変更・実装漏れ

作成日：2026/6/22

参照指摘表：

## 考慮漏れ（1）：DELETE のリクエストボディで review_id を受け取っていた

### 発生した問題

`DELETE /users/{user_id}/reviews/{review_id}` のエンドポイントが、削除対象の識別子として `ReviewDeleteRequest`（リクエストボディ）の `review_id` を使用していた。URL パスに `{review_id}` が既に存在するにも関わらず、リクエストボディの値を使っていた。RFC 9110 では DELETE のボディは意味を持たないと定義されており、REST 原則では「リソースは URL で識別する」とされている。

### 本来どの工程で発見すべきだったか

**設計工程**で発見すべきだった。

`{review_id}` が URL に含まれる時点で、リクエストボディの `review_id` は冗長かつ不適切。ユーザー情報削除で同様の指摘があり、横展開チェックで事前に発見できた（今回は横展開で発見）。

### 教訓

- DELETE の削除対象は URL パスパラメータで受け取る（リクエストボディは不要）
- ユーザー情報削除（指摘 No.1）との横展開で発見できた。設計・実装時に同種エンドポイントを横断チェックする習慣をつける

## 考慮漏れ（2）：設計書にバリデーションエラー表が未記載

### 発生した問題

`review_id` を URL パスパラメータ（int型）に変更したにも関わらず、設計書の引数定義にバリデーションエラー表（review_id が整数以外の場合 → HTTP 422）を追加しなかった。ユーザー作成設計書には同様のバリデーションエラー表が存在しており、記載の統一が必要だった。

### 教訓

引数の受け取り方（リクエストボディ → パスパラメータ）を変更した場合、バリデーションエラーの発生源が変わる。設計書を更新する際は、既存の他エンドポイントの設計書を参照し、バリデーションエラー表の記載パターンを統一する。

---

## 考慮漏れ（3）：結合テスト仕様書のテストケースが設計変更に対応していなかった

### 発生した問題

リクエストボディ廃止に伴い、以下の既存テストケースが意味をなさなくなった。
- No.3「ボディの review_id なし → 422」: リクエストボディが廃止されたため不要
- No.5「URLとボディのreview_idが異なる場合の確認」: リクエストボディが廃止されたため不要

また、URL パスパラメータ review_id に整数以外を指定した場合（/reviews/abc → 422）のテストケースが未記載だった。

### 教訓

引数の受け取り方を変更した場合、既存のテストケース（バリデーションに関するもの）も見直す。旧仕様に基づいたテストケースは削除し、新仕様に基づいたテストケースを追加する。

---

## 考慮漏れ（4）：使用しなくなった ReviewDeleteRequest が schemas.py に残存

### 発生した問題

エンドポイントを `ReviewDeleteRequest`（リクエストボディ）からパスパラメータ `review_id: int` に変更したにも関わらず、`schemas.py` に `ReviewDeleteRequest` クラスの定義が残存しており、デッドコードになっていた。

### 教訓

エンドポイントの引数形式を変更した際は、使用しなくなったスキーマが残っていないか確認し、デッドコードを削除する。ユーザー情報削除・取得でも同様の漏れが発生しており、このパターンへの注意が必要。

## 付記：crud.py の既存バグを 2 件発見・修正

結合テスト作成時に、`create_review` 関連の既存バグを発見した。

### バグ（1）：Review モデルのカラム名誤り

- 誤: `Review(review=review_item, ...)` → 正: `Review(review_item=review_item, ...)`
- SQLAlchemy モデルのカラム名は `review_item` だが、`review` と誤記されていた

### バグ（2）：ReviewManagement 作成時のインデックス誤り

- 誤: `review_date_list[review_time]` → 正: `review_date_list[review_time - 1]`
- `review_time` は 1 始まりの整数（1〜5）だが、リストは 0 始まりのため、インデックス 5 で IndexError が発生していた

これらは単体テストではモック化により隠れていたバグであり、結合テストを作成したことで初めて発見できた。
