## 考慮漏れ（1）：`study_date == ""` チェックがデッドコード

### 発生した問題

`create_review_endpoint` の入力チェックにて、`study_date` の空文字判定が記述されているが、これはデッドコードだった（`main.py:377`）。

```python
# main.py:375-377
if review_create_request.study_date is None or review_create_request.study_date == "":
```

`study_date` は `schemas.py` で `datetime | None` と定義されているため、Pydantic がリクエストのバリデーション時に空文字 `""` を `datetime` 型に変換しようとして ValidationError を発生させる。空文字が `create_review_endpoint` の処理に到達することはなく、`== ""` の比較は永遠に `True` にならない。

### 本来どの工程で発見すべきだったか

**実装工程のコードレビュー**で発見すべきだった。

Pydantic では `datetime | None` のフィールドに空文字を渡すと、モデルのバリデーション段階で ValidationError となり、エンドポイントの処理ロジックに到達しない。この挙動を理解していれば、空文字チェックを実装する必要がないとわかったはず。単体テストコードを記述する際に `study_date=""` をテストデータとして使おうとしたときに、`model_construct` を使わなければ検証を回避できないことに気づき、デッドコードと判明した。

### 見落とした理由

Pydantic の型バリデーション挙動（`datetime` 型フィールドへの空文字入力が ValidationError になること）の理解が不足していた。`str | None` のフィールドでは空文字チェックが必要だが、`datetime | None` では不要という区別が実装・レビュー時に意識されなかった。

## 考慮漏れ（2）：`ReviewSchedule.review_time` のバリデーション範囲が誤っていた

### 発生した問題

`schemas.py` の `ReviewSchedule` クラスにて、`review_time` のバリデーションが `Field(ge=1, le=1)` となっており、値 `1` のみしか許容しない状態だった（`schemas.py:174`）。設計上は `ge=1, le=5`（1 〜 5 回）が正しい。

```python
# schemas.py:174（修正前）
review_time: int | None = Field(default=None, ge=1, le=1)  # le=1 は誤り

# 修正後
review_time: int | None = Field(default=None, ge=1, le=5)
```

単体テストで `review_time=2` や `review_time=3` を含むテストデータを使ったところ、`ValidationError: Input should be less than or equal to 1` が発生して判明した。

### 本来どの工程で発見すべきだったか

**実装工程のコードレビュー**で発見すべきだった。

`Field(ge=1, le=5)` の `le` は「最大値が 5」を意味するが、誤って「最大桁数が 1（＝1桁）」と認識し `le=1` と実装した技術的な誤解が原因。レビューで `ge` と `le` の意味と設計書の定義を照合していれば検出できた。

### 見落とした理由

Pydantic の `Field` において `le` が「less than or equal to（値の上限）」であることを正確に理解していなかった。`le=1` でも動作はするため（ValidationError を出さずに通常の処理は進む）、機能テストで `review_time=1` しか使っていない段階では気づけなかった。

## 考慮漏れ（3）：レスポンスに復習項目 ID が含まれていない

### 発生した問題

`ReviewCreateResponse`（`schemas.py:180`）および `ReviewGetResponse`（`schemas.py:214`）のレスポンスに、復習項目を識別する ID（`review_id`）が含まれていなかった。

復習項目更新 API では `review_id` を指定してリクエストを送る必要があるが、作成後・取得後のレスポンスに `review_id` が含まれていないため、ユーザーは更新対象の `review_id` を知る手段がない。

### 本来どの工程で発見すべきだったか

**設計工程**で発見すべきだった。

API 全体を俯瞰して「作成→更新」「取得→更新」という操作の流れを追ったとき、更新 API に必要な `review_id` をどこで取得するかを設計段階で検討していれば、作成・取得レスポンスへの `review_id` 追加が必要と気づけた。設計工程レビューで「更新 API の前提条件として必要な情報が取得 API で得られるか」という観点のチェックが行われなかった。

### 見落とした理由

各 API エンドポイントを個別に設計・レビューしており、エンドポイント間の依存関係（「A の結果を使って B を呼ぶ」という操作順序）を考慮したレビューが行われなかった。

### 教訓

CRUD 操作の設計レビューでは、各エンドポイントの入出力仕様を個別に確認するだけでなく、「ユーザーが一連の操作を行う際に必要な情報が各レスポンスから得られるか」をシナリオベースで検証する。
