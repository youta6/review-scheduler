# 有効ユーザー検証のデッドコード

作成日：2026/6/23

対象実装ファイル：`app/auth.py`（get_current_active_user 関数）

---

## 発生した問題

`get_current_active_user` に以下の例外処理が実装されていた。

```python
# 3. 削除済みユーザー確認
if user.delete_flag:
    raise HTTPException(status_code=400, detail="削除済みのユーザーです")
```

この条件は到達不能なデッドコードだった。`get_user` が `delete_flag == False` でフィルタするため、`user` が `None` でない場合は常に `delete_flag == False` であり、`if user.delete_flag:` が真になることはない。

---

## 原因

`get_current_active_user` を実装した際、呼び出し先の `get_user` が `delete_flag == False` でフィルタしていることを把握していなかった。

「削除済みユーザーをブロックする必要がある」という意図は正しかったが、`get_user` の時点で既に削除済みユーザーは `None` として返されるため、その後に `delete_flag` を直接チェックしても条件が真になることはない。呼び出す関数の仕様（何を返し、何をフィルタするか）を確認せずに実装したことで、意図通りに動作しない例外処理が混入した。

---

## 本来どの工程で発見すべきだったか

**実装工程**で発見すべきだった。

`get_user` の実装を確認すれば `delete_flag == False` でフィルタしていることがわかる。`get_current_active_user` を実装・レビューする際に `get_user` の仕様を参照していれば、`if user.delete_flag:` が到達不能であることに気づけた。

---

## 教訓

関数を呼び出してその戻り値を使うコードを書くときは、呼び出し先の関数が何をフィルタ・保証しているかを確認してから後続の条件分岐を設計する。

- `get_user` が `None` を返した場合のチェックは必要だが、`user` が非 `None` であった時点で `delete_flag == False` は保証されている
- 「この条件は実際に HTTP リクエストを通じて到達できるか」を、認証フロー全体の流れで確認する
