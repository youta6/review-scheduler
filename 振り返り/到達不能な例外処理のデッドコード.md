# 到達不能な例外処理のデッドコード

作成日：2026/6/23

参照指摘表：
- `レビュー指摘表/結合テスト工程/テスト実施中/復習項目操作/復習項目削除_v0.1_レビュー指摘表.md`（No.5）

---

## 発生した問題

`delete_review_endpoint` に以下の例外処理が実装されていた。

```python
if auth.delete_flag:
    raise HTTPException(status_code=403, detail="削除済みユーザーのため更新できません")
```

しかし、この条件は HTTP リクエストを通じて到達することができないデッドコードだった。

再鑑者（youta6）が結合テスト仕様書から「削除済みユーザーによるアクセス」テストケースが削除されていることに気づき、質問として指摘された。

---

## 原因

`auth.py` の `get_user` 関数は `delete_flag == False` でフィルタしている。

```python
select(User).where(
    User.user_name == user_name,
    User.delete_flag == False  # 削除済みユーザーはNoneになる
)
```

そのため、削除済みユーザーが有効な JWT トークンでリクエストを送っても、認証層で None が返り `credentials_exception`（HTTP 401）が発生する。エンドポイントの `if auth.delete_flag:` には到達しない。

認証フロー全体を把握せずに例外処理を設計・実装したため、実際には到達不能な条件分岐が生まれていた。

---

## 本来どの工程で発見すべきだったか

**設計工程**で発見すべきだった。

エンドポイントに例外処理を追加する際に、「その条件はどのような操作によって発生するか」を認証フロー全体の観点から確認していれば、`auth.py` が削除済みユーザーを先にブロックすることに気づけた。

---

## 教訓

エンドポイントに例外処理を追加する際は、その条件が実際に HTTP リクエストを通じて到達可能かどうかを確認する。

- 認証層（`auth.py`）がどのような条件でリクエストを弾くかを把握した上で、エンドポイント内の例外処理を設計する
- 「削除済みユーザーが操作した場合」のような条件は、認証層で先に処理されていないかを確認する
- 単体テストではモック化により到達不能な条件でもテストできてしまうため、結合テストや認証フローの通しレビューで発見する

到達不能なコードは、テストで「PASSED」になっても意味がない。設計・実装時に到達可能性を考慮する。
