## 考慮漏れ：`UserDeleteRequest.password` フィールドの削除漏れ

### 発生した問題

`schemas.py` の `UserDeleteRequest` クラスに `password` フィールドが残っていた（行67）。

設計工程レビューにて「JWT認証済みの操作であるためパスワード照合は不要」という指摘（CLUD/ユーザー操作/ユーザー情報削除_レビュー指摘表 No.3）が入っており、`main.py` での実装は修正されていたが、`schemas.py` のリクエストクラスへの反映が漏れていた。

```python
# schemas.py:67（単体テスト時点）
class UserDeleteRequest(BaseModel):
    user_id: int
    password: str = Field(min_length=1, max_length=32)  # ← 削除すべきフィールドが残存
```

合わせて `crud.py` の DELETE 処理も `hashed_password` を WHERE 条件に使っていた部分の修正が必要。

### 本来どの工程で発見すべきだったか

**実装工程のコードレビューおよび再鑑**で発見すべきだった。

経緯は以下の通り：

| 工程 | 状況 |
|---|---|
| 設計工程レビュー | 「パスワード照合不要」の指摘あり（指摘No.3）|
| 実装工程 | `main.py` の処理は修正済み。ただし `schemas.py` へのフィールド削除反映が漏れた |
| 実装工程レビュー | `schemas.py` の変更漏れを見落とし |
| 実装工程再鑑 | 同様に見落とし |
| 単体テスト工程 | テストコード記述時に発覚 |

設計工程で既に指摘が入っていたにもかかわらず、実装工程での横展開（`schemas.py` 修正）と、そのレビューでの確認の両方が漏れた。

### 見落とした理由

設計工程レビューの指摘に対する修正範囲として `main.py` の処理変更のみに注目し、`schemas.py` のリクエストクラス定義への影響確認が行われなかった。レビュー・再鑑ともに設計工程指摘一覧との突き合わせが不十分だった。

### 教訓

設計工程レビューの指摘に対する実装工程での修正を確認する際は、処理コード（main.py）だけでなく、リクエスト/レスポンスのスキーマ定義（schemas.py）や DB アクセス層（crud.py）への影響も含めて確認リストを作成する。
