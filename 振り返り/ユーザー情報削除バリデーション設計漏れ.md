# ユーザー情報削除 — 設計変更後のバリデーション記載漏れ

作成日：2026/6/22

参照指摘表：
- `レビュー指摘表/結合テスト工程/テスト実施中/ユーザー操作/ユーザー削除_v0.1_レビュー指摘表.md`（No.2、No.3）

---

## 考慮漏れ（1）：設計書にバリデーションエラー表が未記載

### 発生した問題

HTTP慣習違反の指摘（No.1）対応として `user_name`（リクエストボディ）を廃止し、`user_id`（URLパスパラメータ、int型）に変更した。しかし設計書の引数定義にバリデーションエラー表を追加しなかった。ユーザー作成設計書には「必須パラメータが未指定または型不一致 → HTTP 422」の表が存在しており、記載の統一が必要だった。

### 本来どの工程で発見すべきだったか

**設計書更新時**に発見すべきだった。

ユーザー作成設計書を参照すれば、引数定義の下にバリデーションエラー表を記載するパターンが確認できた。設計変更後に他のエンドポイントの設計書と照合する手順が抜けていた。

### 見落とした理由

旧実装では `UserDeleteRequest`（Pydantic BaseModel）がバリデーションを暗黙的に担っており、設計書上に明示的なバリデーションエラー表が不要だった。パスパラメータに変更することで FastAPI が型チェックを自動送出するようになったが、その変化に伴う設計書の追記を意識できていなかった。

### 教訓

引数の受け取り方（リクエストボディ → パスパラメータ）を変更した場合、バリデーションエラーの発生条件・発生源が変わる。設計書を更新する際は、同種のエンドポイント（ユーザー作成など）の設計書を参照し、記載パターンが統一されているか確認する。

## 考慮漏れ（2）：結合テスト仕様書にバリデーションエラーのテストケースが未記載

### 発生した問題

`user_id` をパスパラメータ（int型）に変更したにも関わらず、結合テスト仕様書にバリデーションエラー（`DELETE /users/abc` など整数以外の値 → HTTP 422）のテストケースを追加しなかった。ユーザー作成結合テスト仕様書には同様の 422 テストケースが含まれており（No.4・No.5）、テストケース設計の統一が必要だった。

### 本来どの工程で発見すべきだったか

**テスト仕様書更新時**に発見すべきだった。

設計書更新の際にバリデーションエラー表を追加していれば、その時点でテスト仕様書への 422 テストケース追加も連動して気づけた。また、他の結合テスト仕様書との比較確認でも発見できた。

### 見落とした理由

旧実装では Pydantic のバリデーションエラーは結合テストで明示的にテストしていなかったため、「バリデーションエラーは結合テストでテストするもの」という認識が薄かった。パスパラメータに変更したことで 422 が発生するケースができたが、テストケースへの反映を失念した。

### 教訓

引数の型を持つパスパラメータを追加・変更した場合、型不一致（例: int 型パスパラメータに文字列を渡す）のテストケースを結合テスト仕様書に追加する。ユーザー作成など既存のテスト仕様書を参照し、422 テストケースの記載パターンを踏襲する。
